# TravelingHub 开发与验收教训清单

> 目的：把一次问题复盘变成后续开发、测试和发布都能执行的规则，避免用户承担定位成本。

## 适用范围

本文适用于 TravelingHub 的前端、Go API、Vite 代理、Docker Compose、PostgreSQL、Redis 与自动化测试。

## 本次暴露的问题

### 1. 通用错误提示掩盖了可修复的问题

前端曾把多个失败状态统一显示为“暂时无法连接远行小屋，请稍后重试”。这使用户无法判断是密码不符合要求、会话过期、来源校验被拒绝，还是服务真的不可用。

规则：

- `400`：显示字段级、可行动的校验提示，例如“密码至少 12 位”。
- `401`：提示重新登录。
- `403`：区分首次改密受限会话与来源/权限被拒绝。
- `5xx`、网络失败：才显示服务暂不可用及重试入口。
- 前端不得把已知 API 业务错误伪装成网络错误。

### 2. 前后端密码规则不一致

前端输入框只要求至少 8 位，而后端密码哈希服务要求至少 12 位。用户能提交前端允许的密码，却收到后端 `400`。

规则：

- 密码、邮箱、分页、枚举等规则必须有单一事实来源。
- 后端是安全规则的最终裁决者；前端必须复用同一契约或同步生成的配置。
- 对每条约束至少覆盖：前端阻止、后端拒绝、后端错误到用户提示的映射。

### 3. 本地浏览器来源与后端来源校验不一致

浏览器以 `http://127.0.0.1:5173` 访问，后端却使用 `http://localhost:5173` 作为可信来源。首次改密的 `POST` 被 CSRF 来源校验拒绝。

规则：

- `TRAVELINGHUB_WEB_ORIGIN` 是部署配置，必须由 Compose 显式传入应用容器。
- 本地默认访问地址、`.env.example`、Vite 启动地址与运行中容器配置必须一致。
- 生产环境只允许精确的 HTTPS 来源；不要为了本地便利放宽生产来源校验。
- 每次发布都检查运行中容器的实际环境变量，而不只检查仓库文件。

### 4. Mock E2E 不能证明真实服务可用

Mock E2E 会拦截浏览器请求并伪造接口响应，适合验证页面流程；它不会发现 API、Cookie、代理、Docker 环境变量、CSRF、数据库或 Redis 的衔接问题。

规则：

| 测试层 | 目标 | 是否 mock API |
| --- | --- | --- |
| 单元测试 | 函数、状态转换、错误映射 | 是 |
| Mock E2E | 表单、按钮、页面跳转、视觉 | 是 |
| 真实服务 E2E | 浏览器到 API、会话、数据库的完整链路 | 否 |
| 集成测试 | API、数据库、Redis、权限与调度 | 否 |

真实服务 E2E 至少覆盖：

1. 随机邮箱注册 Agent；
2. 初始密码登录；
3. 首次改密成功并得到 `204 No Content`；
4. 页面自动进入旅人状态；
5. 刷新后会话和旅人状态仍存在；
6. 密码少于最小长度时给出明确提示；
7. 会话失效、错误来源和跨用户访问都被拒绝。

### 5. 集成测试不得连接开发数据

旧的集成测试会清空运行中的开发数据库，造成测试数据和用户数据混用。

规则：

- 单元测试不连接共享数据库。
- 集成测试只使用 `travelinghub_test` 或一次性容器数据库。
- 真实 E2E 使用独立数据库、Redis 命名空间、端口和测试邮箱域名。
- 测试结束销毁整个测试环境；不要通过清空开发库来“清理”。
- 测试日志、HAR、截图和报告不得包含密码、API Key、Session Cookie 或原始数据库导出。

## 必做测试门禁

TravelingHub 的任何用户可见功能，都必须完成以下五类测试；它们互相补充，不能以其中一类替代另一类。

| 测试类型 | 必测内容 | 通过条件 |
| --- | --- | --- |
| 单元测试 | 领域规则、状态机、密码与输入校验、错误映射 | 成功、边界和失败分支都有自动化断言 |
| 集成测试 | Go API、PostgreSQL、Redis、会话、权限隔离、Worker 持久化 | 使用独立测试数据库，真实依赖连接通过 |
| API/契约测试 | 请求字段、响应字段、HTTP 状态码、Cookie 与错误码 | 前后端对成功与每个重要 `4xx`/`5xx` 的约定一致 |
| Mock E2E | 页面交互、表单、页面状态、重试、可访问性、视觉 | 浏览器流程可重复执行，接口由测试桩精确控制 |
| 真实 E2E | 浏览器、前端、代理、API、Redis、PostgreSQL 的完整链路 | 在隔离环境中完成真实注册、登录、改密、旅人读取与刷新 |

真实 E2E 产生的数据必须写入一次性测试环境，例如 `travelinghub_e2e` 数据库和专用 Redis；测试结束后销毁整个环境。严禁使用开发库、用户库或“插入后手动删除”的方式做真实 E2E。

## 验收结论的分级

禁止用“测试通过”笼统宣称功能可用。验收报告必须明确标注：

- **单元测试通过**：局部逻辑正确。
- **集成测试通过**：服务模块与持久化契约正确。
- **API/契约测试通过**：前后端 HTTP 契约正确。
- **Mock E2E 通过**：浏览器交互和页面投影正确。
- **真实服务 E2E 通过**：真实浏览器、代理、API、会话、Redis、数据库链路正确。
- **人工验收通过**：用户在目标环境成功完成关键任务。

只有关键路径完成真实服务 E2E 后，才可以称为“本地可用”；生产可用还需要 HTTPS、真实邮件投递、备份恢复演练和部署环境验收。

## 开发前检查清单

- [ ] 新的用户输入规则已定义唯一来源与错误文案。
- [ ] API 的成功、校验、鉴权、权限和服务失败状态都已列出。
- [ ] 前端是否需要根据不同状态显示不同的可行动提示已明确。
- [ ] 新增状态变更接口是否有 CSRF、来源校验和 Cookie 策略。
- [ ] 测试数据、测试数据库和开发数据库是否物理隔离。

## 提测前检查清单

- [ ] 单元测试覆盖成功、边界和失败路径。
- [ ] Mock E2E 覆盖用户主要交互、重试和页面可访问性。
- [ ] 真实服务 E2E 覆盖至少一条完整成功链路和每个重要失败分支。
- [ ] 前端不会把已知 `4xx` 业务错误显示成网络错误。
- [ ] 浏览器访问地址、Vite 代理、API 可信来源、Cookie 属性在运行环境中一致。
- [ ] 集成测试没有连接开发或用户数据库。

## 发布前检查清单

- [ ] `go test`、集成测试、静态分析和竞态检测通过。
- [ ] 前端单元测试、lint、构建、Mock E2E、视觉基线通过。
- [ ] 真实服务 E2E 通过，并保存不含敏感数据的结果摘要。
- [ ] 运行中服务健康检查通过。
- [ ] 运行中容器环境变量与发布配置一致。
- [ ] 生产环境使用 HTTPS、精确来源校验、真实邮件验证和独立密钥。
- [ ] 数据库备份、恢复路径与回滚策略已验证。

## 发现问题后的处理原则

1. 先记录真实 HTTP 状态、响应类别、浏览器来源和服务端配置。
2. 不要根据页面上的通用报错猜测原因。
3. 在修复前先增加能复现该问题的自动化测试。
4. 修复后至少重新运行受影响层级的测试；涉及代理、Cookie、来源或配置时必须运行真实服务 E2E。
5. 如果测试影响了用户数据，立即停止后续写入、说明影响、恢复账号或数据，并修复隔离机制。
